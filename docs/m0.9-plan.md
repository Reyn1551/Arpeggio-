# M0.9 plan — automatic context selection

Status: **proposed, awaiting owner approval.** Branch: `feat/m0.9-context-selection` (nothing
committed yet). This file is a working plan, not project documentation; it is deleted or
folded into `docs/` before the milestone is declared done.

## Why this milestone

M0.8 closed with the measured finding that **the edit format is not the binding constraint**:
with `middle` at $0 on the tuning split, three runs per format gave mean solved 1.33 (`udiff`),
1.67 (`whole-file`), 1.00 (`search-replace`); neither candidate reached the +2 required, and
both lost `carboncompare-tree-no-carbon`. The roadmap therefore points the next milestone at
**prompt design and context selection**, so that v1 can start.

Of the two, context selection is the one with a mechanism: today every file the model may
touch must be named by hand in `context_files` in the eval task. If a task forgets a file the
diff touches, the attempt fails as `patch_unknown_path` (M0.7) no matter how good the model is
— a harness limitation wearing the costume of a model failure. That is the same failure shape
M0.8 found in formats.

## What exists today

| Piece | Location | Behaviour |
|---|---|---|
| `read_context` | `orchestrator/patch.py:688` | Reads exactly the paths given, in order, until `CONTEXT_CAP_BYTES` (100 KB). Skips hidden tests, secret-pattern names, non-files, non-UTF-8, and anything over the cap. |
| `build_prompt` | `orchestrator/patch.py:732` | Lists those exact paths as the only files the diff may modify. |
| `context_files` | `evals/task.py:134` | A hand-written list on each eval task. |
| `context_bytes` / `prompt_chars` | `evals/budget.py:54,81` | Worst-case cost estimate from those same paths, sizes read via `git cat-file -s` at `base` (no worktree). |

So selection is entirely manual, and the cost estimate is exact only because the selection is
known before the worktree exists. Any automatic selector must preserve that property.

## Proposed design

Add a **selector** that turns a task request plus the repo's tracked file list into a ranked
list of context paths, behind an explicit option, defaulting to today's behaviour.

1. **`orchestrator/context.py`** (new, pure, no I/O beyond a passed-in file list):
   - `Candidate` (path, size) and `rank(request, candidates, *, limit_bytes, max_files) -> list[str]`.
   - Scoring is **deterministic and explainable**, in the spirit of ADR-0003 (rules before
     learning): token overlap between the request and the path *and* the file's basename
     (a request naming `mul` or `calc.ops` must beat a request naming nothing), a strong bonus
     for a path whose basename appears verbatim in the request, a small penalty for path depth
     and for vendor/build directories (`.venv`, `node_modules`, `dist`, `vendor`, lockfiles).
   - A hard byte cap and file cap, filled in rank order; ties broken by path for stable output.
2. **`read_context` gains a selector path**: when a task supplies no `context_files`, the
   candidate list comes from `git ls-files` at `base` and the selector picks. Hidden tests,
   secret patterns and the existing caps stay enforced in the same place, so the safety
   surface does not move.
3. **Deselecting is not the same as forbidding.** A path the selector did not choose must not
   become `patch_unknown_path` merely because it was not *shown*. M0.7's rule stays: unknown
   means not in the base commit. This needs care and its own test — it is the main correctness
   risk in this milestone.
4. **Budget parity.** `context_bytes` must compute the selector's sizes through the same code
   path the real attempt uses, or the estimate and the run will disagree. This is a test, not
   a hope: estimate and actual prompt must be asserted equal on a fixture repo.
5. **Opt-in, measurable.** `--context-selection manual|auto` on `eval run` (default `manual` =
   today), recorded on the run next to `edit_format`, so `eval matrix` can group by it exactly
   as M0.8 grouped by format. `arpeggio run` stays on `manual` until the experiment accepts
   `auto`.

## Evidence this milestone must produce

The M0.8 experiment is the template and its discipline carries over:

- A fixed acceptance rule written down **before** any run (candidate accepted only if mean
  solved beats the `manual` runs in the same matrix by at least +2, and no task solved under
  `manual` is unsolved in more than one candidate run).
- N=3 rounds per arm, tuning split, `middle` at $0, holdout untouched.
- `eval matrix` output with the verdict, and the numbers in `docs/06-EVALUATION.md` and the
  CHANGELOG either way — **a negative result is a result** and M0.8 is the proof this project
  reports them.

rule 7. Both are in the plan rather than discovered later.

## Explicitly out of scope

- Prompt wording changes (the other half of the roadmap sentence) — a separate milestone.
- Any network call, provider change, or model change.
- Touching `routing/`, `cost/`, `verify/`, `intake/` logic. Note that steps 2–4 touch
  `orchestrator/` and `evals/`, which under AGENTS.md rule 5 does **not** itself require the
  eval gate, but the experiment in step 8 is the gate's evidence anyway.
- Reading anything under `evals/holdout/` or hidden fixtures (AGENTS.md rule 3).

## Risk

The honest risk is that automatic selection does not beat manual, because a hand-written
`context_files` on a curated suite is already a strong baseline — the author knew the answer.
M0.8 was exactly this shape and returned a negative. The design keeps the blast radius small
(default `manual`, opt-in flag, `arpeggio run` untouched) so a negative costs tooling and
knowledge, not a regression.
